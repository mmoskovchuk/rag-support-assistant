# 02. Python-сервіс: розбір коду

Модулі в порядку, в якому їх варто читати: від простих і незалежних до тих, що все збирають разом.

```
config ─┬─ file_store ────────────────────┐
        ├─ ocr ── extraction ── chunking ─┤
        ├─ topics ────────────────────────┤
        ├─ vector_store ──────────────────┼─ ingestion ─┐
        └─ qa ────────────────────────────┘             ├─ api ── static/index.html
logging_setup ──────────────────────────────────────────┘
```

---

## `config.py`: налаштування

Клас `Settings` (Pydantic Settings) читає змінні оточення: `OPENAI_MODEL` стає `settings.openai_model`. Що це дає:

- **Валідація при старті.** Якщо `CHUNK_SIZE=abc`, сервіс не запуститься і чітко скаже чому.
- **Секрети як `SecretStr`.** При випадковому логуванні виводиться `**********`, а не ключ.
- **Одне місце для всіх параметрів.** Решта коду не знає про `os.environ`.

`@lru_cache` на `get_settings()` означає, що файл `.env` читається один раз.

## `logging_setup.py`: логування

Кожен рядок логу містить `request_id`:
```
2026-10-01 12:00:01 INFO     [a1b2c3d4e5f6] support_rag.ingestion: policy.pdf: 3 page(s) -> 12 chunk(s)
```
`contextvars.ContextVar` зберігає значення окремо для кожного запиту, навіть коли запити обробляються паралельно в різних потоках. n8n може передати власний `X-Request-ID`, і тоді виконання workflow і логи API зв'язуються одним id.

## `file_store.py`: життєвий цикл файлу

```
inbox/ ──claim──▶ processing/ ──▶ processed/2026-10-01/file.pdf (+ file.pdf.txt)
                       └────────▶ failed/file.pdf (+ file.pdf.error.json)
```

Головна ідея: **`rename` в межах однієї файлової системи атомарний**. Файл у будь-який момент перебуває рівно в одній папці, навіть якщо живлення зникло посеред операції. Тому `claim()` водночас слугує блокуванням: якщо два запити одночасно спробують забрати файл, `rename` вдасться лише одному.

Варто звернути увагу на `resolve_inbox_file()`: він приймає лише «голе» ім'я файлу. Запит `{"filename": "../../etc/passwd"}` буде відхилено. Це класична вразливість path traversal.

## `ocr.py`: розпізнавання тексту

Цей модуль викликається лише для того, що справді є картинкою: сторінок-сканів у PDF і файлів-зображень.

1. **Сторінка PDF** → `pdf2image` (обгортка над Poppler) рендерить **одну сторінку** в зображення 300 DPI. Якщо рендерити всі одразу, 200-сторінковий PDF займе гігабайти RAM.
2. **TIFF** може бути багатосторінковим (типовий формат сканерів), тому обходимо кадри через `ImageSequence`.
3. **Препроцесинг:** поворот за EXIF, відтінки сірого, автоконтраст. Дешеві кроки, що помітно покращують точність на блідих сканах.
4. **Tesseract:** `lang="ukr+eng"` для змішаних документів; `--oem 1` вмикає нейромережевий рушій LSTM; `--psm 3` вмикає автоматичний аналіз макета сторінки.
5. **`normalise_text()`** прибирає артефакти OCR (і заодно витягнутого з PDF тексту): склеює слова, розірвані переносом (`Від-\nпустка` → `Відпустка`), та зайві пробіли.

Якщо хоч одна сторінка дала помилку, падає весь документ. Це свідоме рішення: частково проіндексований документ гірший за відсутній, бо система впевнено відповідатиме за неповними даними.

## `extraction.py`: текст з будь-якого формату

Єдина точка входу `extract_pages()` повертає список `PageText(page_number, text, method)`, де `method` дорівнює `"text"` або `"ocr"`. Решті пайплайну байдуже, звідки текст.

- **PDF.** Для кожної сторінки `pypdf` спершу пробує взяти **текстовий шар**: так буває в PDF, «надрукованих» з Word чи браузера. Якщо тексту менше за `PDF_MIN_TEXT_CHARS` (30 символів), сторінка вважається сканом і йде в OCR. Чому поріг, а не «порожньо / не порожньо»? Скани часто мають сміттєвий шар з кількох символів, наприклад номер сторінки від сканера.
- **Word (`.docx`).** `python-docx` читає абзаци **і таблиці** в порядку документа (`iter_inner_content()`). Рядок таблиці стає рядком `комірка | комірка`, щоб модель бачила зв'язок «стаж → кількість днів». У Word немає фіксованих сторінок, тому весь текст стає однією «сторінкою» з номером `NO_PAGE = 0`, і цитата виглядає як `[policy.docx]`.
- **Зображення** (PNG, JPG, TIFF) завжди йдуть в OCR.

Імпорти `pypdf` і `docx` всередині функцій мають ту саму мету, що й у `vector_store`: модулі вантажаться лише тоді, коли справді потрібні.

## `topics.py`: тема документа

`TopicNamer.name()` віддає LLM перші `TOPIC_MAX_CHARS` (4000) символів документа і просить назву на 3–8 слів мовою документа. Початку достатньо, бо там зазвичай заголовок і преамбула, а виклик лишається дешевим.

Два захисні механізми:
- відповідь LLM чиститься від лапок і крапки, а занадто довга відповідь відкидається;
- **будь-яка помилка LLM не зупиняє індексацію**: тема береться з назви файлу (`vacation_policy-2026.pdf` → `Vacation policy 2026`). Документ у базі важливіший за красиву назву.

## `chunking.py`: розбиття на чанки

Кожен чанк отримує в метадані `source`, `page` і `topic`. Тема дублюється в усіх чанках документа: ChromaDB зберігає метадані на рівні запису, і так тему можна прочитати з будь-якого знайденого чанка без додаткового запиту.

**Навіщо чанки?** Ембедінг цілого 50-сторінкового документа «розмиває» зміст, і пошук стає неточним. Крім того, в промпт LLM влазить обмежений обсяг тексту.

`RecursiveCharacterTextSplitter` намагається різати по абзацах (`\n\n`), потім по рядках, потім по реченнях і лише в крайньому разі посеред слова. `chunk_overlap=150` означає, що сусідні чанки перекриваються, тож речення на межі не губиться.

Кожна сторінка ріжеться окремо, щоб кожен чанк мав точний номер сторінки для цитування.

**Детерміновані id:** `"<sha256 файлу>:00007"`. Повторна індексація того самого файлу перезапише ті самі записи (upsert), а не створить дублікати. Це називається **ідемпотентність**: операцію можна безпечно повторити.

## `vector_store.py`: ChromaDB + Hugging Face

- `get_embeddings()` завантажує модель `sentence-transformers` через `langchain-huggingface`. `normalize_embeddings=True` нормалізує вектори до одиничної довжини, тому косинусна подібність коректна. Імпорт усередині функції потрібен тому, що `torch` важкий, і тести без нього швидші.
- `_connect()` повторює спробу підключення до 10 разів з експоненційною паузою (бібліотека `tenacity`), бо при `docker compose up` ChromaDB може стартувати повільніше за API.
- Колекція створюється з `{"hnsw": {"space": "cosine"}}`. ChromaDB повертає **відстань** (0 означає ідентичні), а ми перетворюємо її на **relevance** = `1 − distance`, що зрозуміліше для порогу.
- `delete_other_versions()`: коли приходить нова версія `policy.pdf` (інший sha256), чанки старої видаляються, але **лише після** запису нової.

## `ingestion.py`: пайплайн

`ingest()` реалізує зовнішній контур: валідація → очікування → claim → обробка, а в разі будь-якого винятку файл переїжджає в `failed/`. Навіть якщо й переміщення в `failed/` не вдалося (диск повний), файл лишається в `processing/` і повернеться в `inbox/` при наступному старті. Це гарантує, що файл не губиться ніколи.

`_process()` містить логіку: sha256 → перевірка дубліката → видобування тексту → тема → чанки → upsert → прибирання старих версій → архів. У відповіді є `ocr_pages`: скільки сторінок довелося розпізнавати, а не просто прочитати.

### `reindex()`: перебудова без OCR

Після зміни `CHUNK_SIZE`, `CHUNK_OVERLAP` чи `EMBEDDING_MODEL` старий індекс уже не відповідає налаштуванням. OCR при цьому повторювати не потрібно, бо текст кожного документа збережено в `processed/<дата>/<файл>.txt` (формат описано в `archive.py`).

1. `FileStore.list_archives()` повертає пари «оригінал + `.txt`» від найстаріших до найновіших.
2. Якщо той самий файл індексували кілька разів (оновлена версія), береться лише найновіший архів. Решта потрапляє у `skipped_old_versions`, щоб стара версія не «воскресла».
3. Усі архіви парсяться й ріжуться на чанки **до** будь-яких змін у базі. Якщо хоч один архів зіпсований, повертається 422 зі списком проблем, і індекс не змінюється (все або нічого).
4. `VectorStore.rebuild()` записує все в тимчасову колекцію `company_docs__rebuild`, і лише після успіху видаляє стару колекцію та перейменовує нову. Нова колекція потрібна ще й тому, що інша embedding-модель дає вектори іншої довжини, і стара колекція їх не прийме.

`regenerate_topics: true` заново просить LLM назвати кожен документ, наприклад після зміни промпту в `topics.py`.

`threading.Lock` забезпечує, що одночасно обробляється один документ. OCR і ембедінги навантажують CPU на 100%, тож паралельність на маленькому сервері лише створила б конкуренцію за пам'ять.

## `qa.py`: відповідь на питання

Промпт (`PROMPT`) містить кілька важливих інструкцій:
- «Answer ONLY with facts from the context» зменшує галюцинації;
- «reply with exactly NO_ANSWER» дає машинно-зчитуваний сигнал «не знаю»;
- «Answer in the same language as the question» потрібна, бо документи українською, але питання можуть бути англійською;
- «cite its source exactly as the label in square brackets» забезпечує перевірюваність. Мітку формує `source_label()`: `[файл, p. N]` для PDF і `[файл]` для Word.

Ланцюжок `PROMPT | llm | StrOutputParser()` написано мовою **LCEL** (LangChain Expression Language): дані проходять через кроки, як у Unix-пайпі.

`QAService` не знає ні про ChromaDB, ні про OpenAI. Він отримує `retriever` і `llm` ззовні (**dependency injection**). Саме тому в тестах їх легко підмінити на фейкові (`FakeListChatModel`), і тести не потребують API-ключа чи бази.

Два можливі результати:
- `answered`: текст відповіді та джерела, які потрапили в контекст;
- `no_answer` з причиною `no_relevant_context` (нічого не пройшло поріг) або `llm_insufficient_context` (LLM відповіла `NO_ANSWER`). У полі `answer` лежить готовий ввічливий текст, у `topics` до 5 тем, у `sources` найближчі чанки.

**Один пошук на дві цілі.** `ask()` шукає `SUGGESTION_POOL_K` (20) чанків. Перші `TOP_K` (4) кандидати на контекст, а весь пул джерело тем. Чому не 4? Чотири найближчі чанки часто з одного документа, і тоді була б лише одна тема. `distinct_topics()` проходить пул від найближчого до найдальшого і збирає унікальні теми.

**Повідомлення без LLM.** `no_answer_message()` будує текст із шаблону `NO_ANSWER_TEXT`, мову визначає `detect_language()` (є кирилиця → українська). Тут LLM не потрібна: текст передбачуваний, безкоштовний і не може «нафантазувати».

Політика помилок: ChromaDB чи OpenAI недоступні → HTTP 503. Це аварія інфраструктури, а не «відповіді немає», і клієнт має розрізняти ці ситуації.

## `api.py`: FastAPI

- **`lifespan`** виконується один раз при старті: налаштовує логи, відновлює файли після збою, підключається до бази, завантажує модель. Об'єкти зберігаються в `app.state`.
- **Синхронні ендпоінти (`def`, не `async def`).** FastAPI запускає їх у пулі потоків. Якби OCR виконувався в `async def`, він заблокував би весь сервер, включно з `/health`.
- **Мапінг помилок на HTTP-коди** (400/404/409/413/415/422) дає n8n змогу розгалужувати workflow за кодом відповіді.
- **`/`** віддає вебчат (`static/index.html`). Сама сторінка публічна, але кожне запитання з неї йде з `X-API-Key`.
- **`/docs`** містить автоматичну Swagger-документацію; там можна «потикати» API з браузера (кнопка Authorize для ключа).

## Тести (`app/tests/`)

Тести перевіряють логіку, а не зовнішні сервіси:
- `test_file_store.py`: path traversal, ексклюзивність claim, неперезапис файлів, відновлення після збою;
- `test_chunking.py`: номери сторінок, детермінованість id, нормалізація OCR-тексту;
- `test_qa.py`: сценарії рішення (відповідь / нижче порогу / `NO_ANSWER`), збір тем з ширшого пулу, текст повідомлення, визначення мови;
- `test_extraction.py`: змішаний PDF (сторінка з текстом не йде в OCR, скан іде), Word з таблицею в правильному порядку, пошкоджений файл;
- `test_topics.py`: чистка відповіді LLM, велика літера, запасна тема з назви файлу;
- `test_reindex.py`: формат архіву (і старі архіви без заголовка), лише найновіша версія файлу, перегенерація тем, «все або нічого» при зіпсованому архіві.

## `static/index.html`: вебчат

Один файл без бібліотек і збирання: HTML, CSS і ~150 рядків JavaScript.
- `fetch("/ask")` з заголовком `X-API-Key`. Ключ вводиться один раз і зберігається в `localStorage` браузера (обгорнуто в `try/catch`, бо сховище буває недоступним у приватному режимі).
- Весь текст з сервера проходить через `escapeHtml()` перед вставкою в сторінку. Інакше документ, у якому трапився `<script>`, виконав би код у браузері працівника (XSS).
- Цитати `[файл, p. N]` підсвічуються як бейджі, теми з `no_answer` стають кнопками: клік підставляє тему в поле запитання.
- Коди відповіді: 401 → відкрити поле ключа, 503 → «сервіс тимчасово недоступний».
- Світла й темна тема через `prefers-color-scheme`.
